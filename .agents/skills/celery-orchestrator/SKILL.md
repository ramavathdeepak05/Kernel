# Celery Orchestrator Skill

You are the ALIS Automation Expert. Your objective is to design, implement, and debug the 24/7 autonomous background pipelines that power the Event-Driven Autonomy of ALIS.

## Core Directives

1. **Task Chains**: Construct complex, resilient Celery task chains (`chain`, `chord`, `group`) that map to institutional workflows (e.g., Application → OCR → Evaluation → Decision).
2. **Event Pub/Sub**: Ensure strict adherence to the Domain Event Bus pattern. Modules must communicate exclusively via events, never through direct synchronous cross-module HTTP/RPC calls.
3. **Idempotency**: All Celery tasks MUST be idempotent. If an AI evaluation task fails midway, re-running it must not corrupt the database or duplicate records.
4. **Dead Letter & Reviews**: When an automated Celery pipeline fails or hits a policy boundary it cannot resolve, it must route the payload to the module's `review_queue` for human Staff oversight.

## DB Access in Celery Tasks — Critical Rule

Celery workers have **no HTTP request context**. There is no TenantMiddleware, no ContextVar set.
`execute_query` and `execute_transaction` will raise `TenantIsolationError` if called without an explicit `tenant_id`.

**Rule:** Use `execute_system_query` / `execute_system_transaction` in all Beat tasks that operate across tenants.
Use `execute_query(tenant_id=org_id)` / `execute_transaction(tenant_id=org_id)` in event-handler tasks that already know their tenant.

```python
from server.db_service import execute_system_query, execute_system_transaction

# Beat task — no tenant context, reads across all tenants
rows = execute_system_query(
    "SELECT id FROM domain_events WHERE status = 'PENDING' AND retry_count < 3 LIMIT 50",
    (),
)

# Event-handler task — tenant is known from the event payload
from server.db_service import execute_transaction
execute_transaction(
    [("UPDATE applicants SET status = %s WHERE id = %s", ("ENROLLED", applicant_id))],
    tenant_id=org_id,  # explicit — no ContextVar in Celery
)
```

## Workflow: Implementing a New Autonomous Flow

1. Define the triggering domain event (e.g., `FeePaymentReceived`).
2. Draft the `automation_pipeline.py` task chain.
3. Implement `event_publisher.py` for any downstream events generated by the chain.
4. Implement `event_handlers.py` to subscribe to events this module reacts to.
5. Verify idempotency and review queue fallbacks.

## Task Structure Pattern

```python
# server/finance/automation_pipeline.py
from server.worker import celery_app
from server.db_service import execute_transaction, execute_system_query

@celery_app.task(
    name="server.tasks.finance.process_payment_confirmed",
    bind=True,
    max_retries=3,
    default_retry_delay=60,
    acks_late=True,           # Re-queue on worker crash
)
def process_payment_confirmed(self, event_id: str, org_id: str, payload: dict) -> None:
    """Idempotent — uses ON CONFLICT DO NOTHING to prevent duplicates."""
    try:
        applicant_id = payload["applicant_id"]
        amount = payload["amount"]

        # Idempotent write — safe to re-run
        execute_transaction(
            [("""
            INSERT INTO payment_confirmations (id, org_id, applicant_id, amount, confirmed_at)
            VALUES (uuid_generate_v4(), %s, %s, %s, NOW())
            ON CONFLICT (org_id, applicant_id) DO NOTHING
            """, (org_id, applicant_id, amount))],
            tenant_id=org_id,
        )

        # Emit next event in the chain
        from server.core.domain_events import DomainEventBus
        import asyncio
        asyncio.run(DomainEventBus.publish("EnrollmentTriggered", {
            "applicant_id": applicant_id,
            "org_id": org_id,
        }))

    except Exception as exc:
        # Dead letter — route to review queue on final failure
        if self.request.retries >= self.max_retries:
            enqueue_for_review.delay(org_id, "payment_confirmed", payload, str(exc))
        raise self.retry(exc=exc)
```

## Stuck-Event Detection Pattern

When a Celery worker crashes after picking up an event but before completing it, the event
stays in `PROCESSING` state forever. Use `processing_started_at` to detect these.

```python
# In a Beat task targeting critical topics (FINANCE, EXAMINATION)
from server.db_service import execute_system_query, execute_system_transaction

stuck = execute_system_query(
    """
    SELECT id FROM domain_events
    WHERE status = 'PROCESSING'
      AND event_type = ANY(%s)
      AND processing_started_at < NOW() - INTERVAL '2 minutes'
    LIMIT 20
    """,
    (["FINANCE.PaymentConfirmed", "EXAMINATION.GradeFinalized"],),
)
if stuck:
    stuck_ids = [r["id"] for r in stuck]
    execute_system_transaction([
        ("UPDATE domain_events SET status = 'PENDING', processing_started_at = NULL "
         "WHERE id = ANY(%s)", (stuck_ids,)),
    ])
    for row in stuck:
        dispatch_domain_event.delay(row["id"])
```

The `retry-stuck-critical-events` Beat entry in `worker.py` runs every 30 seconds for FINANCE
and EXAMINATION events. Extend it to other topics by adding to the `topics` kwarg list.
